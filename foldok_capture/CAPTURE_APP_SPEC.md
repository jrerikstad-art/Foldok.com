# Capture app — Foldok mode

**Target:** Capture v0.4.0
**Desktop side:** `foldok_capture` (attached, 24 tests green)
**Principle:** Capture stays a camera. Foldok mode is a work list on top of it.

---

## 1. Why almost nothing changes

Three decisions already in Capture v0.3.0 do the hard parts:

**SAF folder binding.** A project links to a folder the user picks — OneDrive, Drive, local. That means the photo reaches the laptop through the customer's own already-approved sync tool. No pairing, no QR, no server, nothing for an IT department to review. This is better than the local-network sync I originally proposed, and it is the reason this feature is small.

**The `extra` slots.** `Project.extra` and `CaptureRecord.extra` are documented as *"a growth point for future layers without a schema migration."* Everything below lands there.

**The instincts.** *"The photo save is the source of truth"*, logging never blocks the shutter, malformed lines skipped rather than poisoning history. Keep all of it.

---

## 2. The one thing that blocks integration

`CaptureLog` writes to `<app documents>/captures/log.jsonl` — app-private. The photo reaches the folder; the record does not. So Foldok sees a JPEG and has no idea which requirement it satisfies, and a human is back to matching photos to gaps by hand.

**Write a sidecar into the linked folder, next to the photo:**

```
IMG_1710000000000.jpg           the photo        (already happens)
IMG_1710000000000.foldok.json   the sidecar      (new)
```

Keep the app-private log as well — it is the phone's own history and it survives the user unlinking a folder.

**One file per capture, written once, never edited.** Not a style choice: a single appended log across two devices over OneDrive produces `log (conflicted copy).jsonl`, and then the evidence trail has two heads. Create-only files sync cleanly everywhere.

---

## 3. Sidecar format

```json
{
  "schema_version": 1,
  "capture_id": "cap_01HX...",
  "file_name": "IMG_1710000000000.jpg",
  "captured_at": 1710000000.123,
  "may_leave": false,
  "project_id": "job_114",
  "gap_id": "a3f19c2b7e04",
  "requirement_key": "el.board_photo",
  "subject": "board:DB1",
  "captured_by": "J. R. Erikstad",
  "device": "Pixel 8",
  "app_version": "0.4.0",
  "checksum": "9f2c…"
}
```

- `checksum` — SHA-256 of the photo, first 32 hex chars. Foldok re-verifies it, so a photo edited after capture is flagged rather than silently accepted as evidence.
- `may_leave` — **always `false` for a photo.** A photograph cannot be masked: nameplate, serial number, client logo, sometimes a face. Foldok's private-call layer blocks it unless a person approves that specific image.
- `location` — **omit unless the user turned it on.** For a compliance record a GPS fix is either proof somebody was on site or a log of a worker's movements, and consent is the difference. Strip EXIF GPS by default.
- `device` — model string only. Never IMEI, serial or advertising id.
- `captured_by` — only if the app already knows a name. Do not prompt for one at the shutter.

## 4. Reading the work list

Foldok writes `.foldok/capture_tasks.json` into the same folder:

```json
{
  "schema_version": 1,
  "project_id": "job_114",
  "project_title": "Storgata 14",
  "generated_at": 1710000000.0,
  "tasks": [
    {
      "gap_id": "a3f19c2b7e04",
      "requirement_key": "el.board_photo",
      "title": "Photograph of the finished board — Hovedtavle",
      "instruction": "Photograph the board with the cover off, labels legible.",
      "subject": "board:DB1",
      "subject_label": "Hovedtavle",
      "authority": "NEK 400:2022 §8-1",
      "severity": "required"
    }
  ]
}
```

The instruction is generated by Foldok's `PhotoCaptureResolver`. Nobody authors capture guidance twice.

**Same channel, both directions.** Read it through SAF like any other file in the folder.

## 5. Dart changes

### D1 — `Project.extra`
```dart
extra: {
  'foldok_project_id': 'job_114',
  'foldok_document_id': 'doc_...',
}
```
Set when the user picks a folder containing `.foldok/binding.json`. If that file is present, the chip is a Foldok job and Foldok mode turns on for it. If not, Capture behaves exactly as today.

### D2 — `CaptureRecord.extra`
```dart
extra: {
  'gap_id': task.gapId,
  'requirement_key': task.requirementKey,
  'subject': task.subject,
  'checksum': sha,
  'may_leave': false,
}
```

### D3 — Sidecar writer
New `lib/storage/sidecar_writer.dart`. Writes the JSON above into the linked folder through SAF, immediately after the photo is written.

**Follow the existing rule: best-effort, never blocks the shutter.** But unlike `CaptureLog`, a failed sidecar write must be *retried*, because without it the photo is unattributed evidence. Queue the retry; do not swallow it.

### D4 — Task list screen
One new screen, reachable from the project chip when the project is a Foldok job:

- open tasks, grouped by subject, each with its instruction and authority
- tap a task → returns to the camera with that task armed; the instruction shows above the shutter
- shutter → photo + sidecar carrying that task's ids → task greys out
- a **Free capture** entry at the top, which is exactly today's behaviour

Do not build: document viewing, gap resolution beyond photos, editing, chat. Each is a worse version of the desktop and doubles what you maintain. The discipline is what keeps this light.

### D5 — Pending capture lifecycle **(behaviour change, and it matters)**

`PendingCaptures` currently discards buffered shots if the app backgrounds without a folder choice — *"nothing lingers as an unsorted pile."* Correct for a standalone camera.

**Wrong for evidence.** A gap-linked capture that vanishes is lost evidence from a site somebody drove two hours to reach, and it is not recoverable.

So: a capture with a `gap_id` is **persisted, not buffered**. It survives backgrounding and app restart, and is retried until it lands in the folder. Show them in the pending banner with a count. Free captures keep today's rule.

This is the only real engineering in the whole feature. Do it properly.

### D6 — Stale list indicator
If `generated_at` is more than a few hours old, say so. It is a snapshot, not a live feed, and someone on site should know their list might have moved.

## 6. Desktop side (already built)

```python
from foldok_capture import bind, publish, tasks_from_gaps, ingest

bind(folder, project_id="job_114", project_title="Storgata 14")
publish(folder, tasks_from_gaps(session.gaps()), project_id="job_114")

report = ingest(folder, session)     # closes gaps, cites the file and the moment
print(report.summary())
```

`ingest` is idempotent, re-verifies checksums, and **never guesses**. A photo with no sidecar, a sidecar for an unknown gap, a sidecar whose photo has not synced yet — each is reported, none is matched by filename or timestamp. Matching a photo to a requirement by guessing is how fabricated evidence enters a compliance document.

It also still matches after a requirement pack version bump, because gap ids hash the pack but requirement + subject is durable.

---

## 7. Definition of done

1. Picking a folder with `.foldok/binding.json` turns on Foldok mode; every other folder behaves exactly as v0.3.0.
2. A task list appears, tapping a task arms it, and the photo lands with a sidecar.
3. `ingest` on the desktop closes that gap with the file and capture time cited.
4. A gap-linked capture survives force-quitting the app and still arrives.
5. EXIF GPS is stripped unless the user turned location on for that project.
6. Free capture is unchanged and still one tap from launch.
